# PLAMX V5 — Gotchas (confirmed pitfalls)

> Each entry: symptom → root cause → rule. Fixed items stay as warnings (regression bait).
> Last reviewed: 2026-10-27.

1. **The selected-plan dashboard card and its task details must use the same filtered task set.** In plan-only scope, show the details' allocated `actual_contribution` as the single progress value; detailed filters continue to show scoped target and achievement metrics. Do not substitute stored plan `progress`, which may diverge from task allocation totals (`ManagementDashboardService::resolvePlanProgressFromTaskDetails`, 2026-10-15).
2. **Historical dashboard snapshots are as-of cutoffs; an explicit selected period is interval-bounded.** For a period, target is the latest measurement point inside the interval and actual is the latest execution inside it. A task without an in-period target contributes no target scope, but its in-period actual contribution is retained; a target of zero likewise retains actual. Keep full precision until aggregation (`app/Services/Dashboard/TaskPeriodProgressCalculator.php`, `ManagementDashboardService::resolveTaskExecutionProgress`, `PlanImpactCalculationService::summarizeMainTasks`, 2026-10-15).
3. **One formula per aggregation level.** Department performance once used average progress while global/employees used weighted `execution_rate` — incomparable numbers. Rule: all levels share `PlanImpactCalculationService::summarizeMainTasks`.
4. **Unrelated plan combinations must not merge silently.** Selecting a strategic + operational plan with no link used to scope by the operational plan only. Rule: intersect + explicit `plan_linkage` warning (`resolvePlanLinkage`).
5. **Filters must propagate identically.** The store once dropped `priority` in reminders and never sent `project_ids`/`task_status_ids`/`kpi_status_ids`. Rule: same filter object to data, drilldown, reminders (`managementDashboardStore.js`).
6. **Zero-weight KPIs are invisible, not zero.** `summarizeKpis` skips weight 0 in the average. Rule: expose `weighted_count`/`unweighted_count` in `data_quality`; never present the average as covering all KPIs.
7. **Negative-polarity KPIs invert.** `target=3000, actual=5000` → 60%, never `actual/target` (166.7%). Always route through `KpiCalculatorService`.
8. **`KpiCalculatorService::calculateKpiVerificationValue` writes to the DB** (updates `verification_value`/`progress`, creates `kpi_executions`, propagates reverse relations). Never call it from a read-only/audit path.
9. **`UpdateTaskProgress` ignores polarity** (linear formula only). Negative-polarity tasks are mis-computed at the source — known, unfixed.
10. **Unattributed `overallPerformance` is absolute, not %.** `actual_contribution` (e.g. 16.02) looks like a low percent next to `execution_rate` (57.4). Always display with `target_scope` context.
11. **Frontend plan filter is pivot-only; backend linkage is pivot + structure.** An op plan linked only via `strategic_structure` looks unlinked in `DashboardFilters.vue` but linked in `resolvePlanLinkage`. Backend is authoritative.
12. **No test DB configured** — see `testing` skill DATABASE SAFETY before running anything beyond mocked unit tests.
13. **`$t` falls back to the source key, not a translated value.** The shared `trans()` helper accepts replacement values as its second argument, but a missing `ar.json` key still renders raw English in Arabic UI. Rule: verify each new `$t` key exists in `resources/lang/ar.json`; use `$term(key, arabicFallback)` when resolving configurable terms.
14. **One editor per file.** Two agents editing the same Vue file concurrently produced duplicate declarations (white-screen crash: `scopeAchievement` ×2) and silently reverted edits. Rule: verify disk bytes (shell read) before each edit batch and right after; work serially (`ExecutiveSituationCards.vue`, 2026-10-13).
15. **Filtered performance must not fall back to all-time values.** Task snapshots use the latest execution through the period end (or KPI initial value); date-filtered KPI sums/snapshots use only observations in scope. As-of-today caps tasks, KPIs, and trend periods at the effective date (`ManagementDashboardService::resolveTaskExecutionProgress`, `KpiPerformanceCalculator::calculate`).
16. **Department team rows must filter roster membership.** Filtering task/KPI data alone leaves employees from other departments visible; `buildScopedEmployeeQuery` must constrain `work_team_members.current_section_id` to the selected department IDs.
17. **An empty period selection means all available data.** `DashboardScope`/`PeriodHelper` treat null as unbounded despite the “Active / Default Period” placeholder; the user confirmed on 2026-10-14 to keep all-data behavior.
18. **Route cache requires unique names for distinct routes.** Keep established route helper names on the canonical route, give alternate routes unique names, and do not suppress `route:cache` failures in CI (`routes/tenant.php`, `.github/workflows/main.yml`, 2026-10-14).
19. **MySQL may leave DDL behind when a migration fails before its migration record is written.** For migrations that must recover from partial execution, check table/column existence before creating them (`2026_10_13_000001_create_task_funding_sources_table.php`, 2026-10-14).
20. **Stored plan progress can diverge from dashboard task allocations.** The current plan-progress jobs average root structures by their relative weights, while the dashboard sums allocated main-task contributions; do not treat the stored plan value as the same metric or rewrite plan data from a dashboard read (`app/Jobs/UpdateOperationalPlanProgress.php`, `app/Jobs/UpdateStrategicPlanProgress.php`, 2026-10-15).
21. **Partial task updates must not detach subtasks.** `TaskService::saveTaskData` updates `parent_task_id` only when the request explicitly contains that field; omission must preserve the existing parent (`app/Services/TaskService.php`, regression tests in `tests/Unit/Tasks/TaskServiceParentTaskTest.php`, 2026-10-15).
22. **Named login redirects must not be overridden by Laravel's global guest redirect callback.** Use `central.login` for central routes and `login` for tenant routes in `Authenticate::redirectTo`; do not configure a global `guests` callback that bypasses this logic (`app/Http/Middleware/Authenticate.php`, `bootstrap/app.php`, 2026-10-15).
23. **Plan task detail totals must use the dashboard's allocated main-task rows.** The plan modal lists main tasks only; target/actual totals use `PlanImpactCalculationService::summarizeMainTasks` so they match the selected scope, and scheduled progress is evaluated through the selected period end (`ManagementDashboardService::buildPlanTaskDetails`, 2026-10-15).
24. **A period filter means scheduled date overlap, not incomplete-task carry-forward.** A task whose due date is before the period start must not leak into the period merely because progress is below 100%; require interval overlap and exclude tasks with both schedule dates missing (`ManagementDashboardService::buildScopedTasksQuery`, `taskOverlapsDateRange`, 2026-10-15).
25. **Plan impact display precision differs from stored/calculated precision.** Allocation ratios are persisted as `DECIMAL(12,6)`; dashboard impact sums use the stored ratio without per-task rounding, while dashboard views truncate only for display to three decimal places (`0.185555` → `0.185`). Never sum the truncated display values; it can make the visible row total lower than the exact aggregate (`0.8085` displays as `0.808` but contributes `0.8085` to the sum). (`2026_09_28_000001_add_allocation_ratio_to_plan_hierarchy_tables.php`, `PlanImpactCalculationService::summarizeMainTasks`, `managementDashboardApp/utils/formatPlanImpact.js`, 2026-10-18).
26. **A date range covering the full task schedule must preserve the initiative's stored progress.** For unfiltered tasks and selected ranges that enclose a task's complete start/due interval, use `Task.progress`; narrower ranges use the latest in-range main-task execution, with dynamic tasks excluding executions outside their task dates (`ManagementDashboardService::resolveTaskExecutionProgress`, 2026-10-19).
27. **Recalculate plan allocations after editing relative weights.** The active `review-weight/progress-weight` flow recalculates the selected plan through `AllocationRatioService`; the legacy `weights-review` flow only updates `relative_weight`, leaving the separate dashboard `allocation_ratio` stale. Do not use the legacy flow to change plan weights (`ProgressWeightReviewService::updateWeights`, `StrategicReportController::updateWeights`, 2026-10-18).
28. **Backfill existing strategic-plan allocations per tenant.** The deployment `tenants:seed --class=Database\Seeders\Tenant\UpdateDataSeeder` runs for all tenants; the seeder recalculates each strategic plan from its current relative weights. Strategic recalculation must include root operational structures linked either through the strategic-structure FK or the strategic-plan/operational-plan pivot, matching dashboard scope. Deploying screen code alone does not rewrite persisted ratios; saving the active screen refreshes only its selected plan (2026-10-18).
29. **Business Center (reports/dashboards) must never determine app access in My Apps / Application Center.** Access to view a report in Reports Center does not grant access to the underlying app; only functional module permissions (`menu` and top-level `permissions`) govern app visibility. In `AccountAppsController`, exclude `reports` and `dashboards` when collecting permissions, and never allow apps with empty permissions to non-super-admins (`app/Http/Controllers/Tenant/General/AccountAppsController.php`, 2026-10-19).
30. **Task period report charts require explicit rendering after report data loads.** The domain performance chart must not depend on a display checkbox. Previous-period comparisons must use the same dashboard task-impact metrics as the selected period before plotting achievement (`actual / target`); legacy quarterly report data can produce a different percentage. Fetch history after the selected period report succeeds (`resources/views/tenant/reports/tasks/period_plan_report.blade.php`, 2026-10-19).
31. **Do not combine `data-control="select2"` with an inline AJAX `select2()` initialization.** Metronic `KTApp.initSelect2` runs on DOMContentLoaded, after inline page scripts, and reinitializes those elements with static options. This removes the AJAX configuration, so the dropdown immediately shows "No results found". Remove the attribute from selects that are initialized manually, or initialize them later, for example on change or when the modal opens (`operational_structure/inputs/levels_inputs.blade.php`, 2026-10-19).
32. **Approval eligibility must not rely on policies.** `BasePolicy::before` returns `true` for Super Admin before normal checks, so a Super Admin who is not the target would pass a policy-only gate. Enforce target/assignment rules in `ApprovalService::isEligible`; `canDecide()` and `decide()` share it (`app/Providers/AuthServiceProvider.php`, `app/Services/Approval/ApprovalService.php`, 2026-10-20).
33. **Active approval deduplication has no DB unique constraint.** `ApprovalService::create` uses a tenant-database-scoped MySQL/MariaDB `GET_LOCK` plus a transaction and `lockForUpdate`, so service callers are serialized; direct inserts or bypassing the service can still duplicate. Keep `entity_id = NULL` creation requests out of deduplication (`app/Services/Approval/ApprovalService.php`, 2026-10-20).
34. **Approval cancellation must merge metadata, not replace it.** Only the stored requester may cancel a `pending`/`returned` request; a non-empty reason is mandatory and goes under `metadata.cancellation_reason` while all other keys stay intact. Do not create an `approval_decisions` row for cancellation (`ApprovalService::cancel`, 2026-10-20).
35. **Approval lock keys must use the column collation, not raw or lowercased strings.** MariaDB compares `entity_type`/`action` case- and accent-insensitively, while `GET_LOCK` names are case-sensitive. `ApprovalService::createLockName` resolves the actual column collation and hashes `WEIGHT_STRING`, so `task`, `Task` and `TÁSK` share one lock (`ApprovalService::createLockName`, 2026-10-20).
36. **Approval creation locks survive only as long as the transaction that owns the insert.** `afterRollBack` is registered on the deepest pending transaction; rolling back a savepoint created before `create()` releases the lock, while rolling back a later savepoint keeps the insert and the lock. Both paths are covered in `ApprovalServiceTest` (`ApprovalService::withCreateLock`, 2026-10-20).
37. **Approval dedupe is transition-aware, not just entity+action.** `ApprovalService::create` reuses an active request only when the latest snapshot matches on the fields the action applies (`status_id` for `status_change`/`task_approval`; `approval`/`quality`/`closed` for the others). Different proposed transitions intentionally create separate active requests, so consumers must match by proposed status instead of assuming a single active request. In the same flow, evidence may auto-approve only on `SKIP_TRIGGER_NOT_MET`/`SKIP_CONDITIONS_NOT_MET`; all other skip reasons stay unapproved (`ApprovalService::matchesProposedState`, `ApprovalAutomationEngine::SKIP_*`, `ResultApprovalAutomationObserver`, 2026-10-24).
38. **Dynamic model properties serialized in `$appends` must be explicitly declared on the Eloquent class.** Eloquent puts undeclared assigned properties into `$attributes`, which `save()` attempts to persist to the database (causing `SQLSTATE[42S22]: Column not found: 1054`). Declare them as `public bool $prop = false;` so PHP handles assignment directly without routing to Eloquent's `__set()` (`app/Models/Task.php`, 2026-10-25).
39. **Deferred status changes pending approval must retain original UI group.** When status change triggers an approval rule, backend defers the status change and keeps original `task_status_id`. Frontend (`TaskTable.vue` and `TasksApp.vue`) must not move the task row to the target status group optimistically; it must stay in place with badge `بانتظار الاعتماد` and an informational toast (`resources/js/tasksApp/`, 2026-10-25).
40. **Task model lifecycle events and KPI/workflow defaults are separated into `TaskObserver` and `TaskDefaultService`.** `Task::booted()` is decoupled into `app/Observers/TaskObserver.php` and `app/Services/TaskDefaultService.php` to maintain Single Responsibility and keep the model thin; registered in `AppServiceProvider::boot` (`app/Models/Task.php`, `app/Observers/TaskObserver.php`, 2026-10-25).
41. **PrimeVue Select/Dropdown search in modals requires explicit modal appending and Arabic normalization.** PrimeVue's Select overlay teleports to `body` by default; Bootstrap 5 modal's focus trap steals input focus from it if the modal has `tabindex="-1"` or if the overlay is not appended inside the modal. In addition, PrimeVue's default `contains` filter uses strict substring matching without normalizing Arabic character variants (hamzas `أ/إ/آ`, taa marbuta `ة/ه`, alif maqsura `ى/ي`, diacritics). Rule: append dropdown overlays to the modal element (`:append-to="selectAppendTarget"` where target is the modal element), remove `tabindex="-1"` from the modal wrapper, and register an Arabic-normalizing filter via `FilterService.register('contains', ...)` in `index.js` (`resources/js/approvalAutomationsApp/`, 2026-10-25).
42. **Multi-level dynamic executions derive aggregated progress without emitting phantom automation events.** When a Level 2 sub-task has `dynamic_execution = 1` and its Level 3 sub-sub-tasks have executions: `UpdateTaskProgress` calculates progress from sub-tasks and calls `createParentTaskExecution`. While `UpdateTaskProgress::$isUpdatingProgress = true`, derived `TaskExecution` inserts/updates on Level 2 and Level 1 bypass `Automation::dispatch(TASK_EXECUTION_*)`, ensuring only the subject leaf execution triggers automation events once, without cascade loops or phantom executions (`app/Jobs/UpdateTaskProgress.php`, `app/Models/TaskExecution.php`, `tests/Feature/Automation/ExecutionAutomationTest.php`, 2026-10-25).
43. **Approval automation actions must be disambiguated by trigger event, not left as generic `approval`.** When creating approval rules in UI, the action config defaults to `action: "approval"`. If multiple rules (e.g. status change, due date change, assignee change) use generic `"approval"`, `ApprovalService::create` deduplicates by `(entity_type, entity_id, action)` and skips creating new requests, erroneously returning a pre-existing request from another trigger. Rule: normalize generic `"approval"` or empty action in `ApprovalAutomationEngine::createApprovalRequest` to the semantic action (`due_date_change` for `task.due_date.changed`, `assignee_change` for `task.assignee.changed`, etc.), and ensure UI badges in `TaskTable.vue` bind specifically to `due_date_deferred_for_approval` and `responsibles_deferred_for_approval` rather than generic `has_pending_approval` showing under the status column (`app/Services/Approval/Automation/ApprovalAutomationEngine.php`, `resources/js/tasksApp/components/items/task-table/TaskTable.vue`, 2026-10-25).
44. **Subsequent field edits while an approval request is pending must be rejected pre-emptively with localized validation messages.** When a field modification (due date, status, responsibles) is deferred for approval, subsequent attempts to mutate that same field while the prior request is `pending` or `returned` must not trigger automation rules again (which previously resulted in skipped duplicate runs and generic errors). Rule: pre-emptively check for active requests on that specific semantic action in observers/controllers and throw a localized `ValidationException` (`"Cannot modify due date while a previous change request is pending approval."`, etc.); similarly, disable frontend inline edit controls and show the pending approval badge on the specific field column (`TaskApprovalAutomationObserver`, `TaskResponsiblesController`, `TaskTable.vue`, `SubTasks.vue`, `TaskDetailView.vue`, `TaskStatusesEditor.vue`, 2026-10-25).
45. **Inline table inputs with both `@blur` and `@keyup.enter` fire duplicate concurrent mutation requests.** When an `<input>` element binds `@blur="save(task)"` and `@keyup.enter="save(task)"`, pressing Enter invokes `save` and immediately causes the input to lose focus/blur, triggering `save` a second time while the first asynchronous API call is still in flight. If the controller or observer is not strictly idempotent, concurrent duplicate runs collide on database unique constraints (e.g. `automation_runs_event_key_unique`), leading to one request succeeding (200 with toast info) while the concurrent twin fails (422 with toast error). Rule: in template, bind `@keyup.enter.prevent="($event.target as HTMLElement)?.blur()"` (or `$event.target.blur()` in plain JS components) so enter delegates exclusively to the blur event; in the save method, guard with `if (isSaving.value || editingId.value !== task.id) return;` and immediately reset `editingId.value = null;` before awaiting the network request; on backend, catch duplicate key exceptions gracefully in `ApprovalAutomationEngine::createRunRecord` to recover in-flight runs (`TaskTable.vue`, `SubTasks.vue`, `TaskDetailView.vue`, `ApprovalAutomationEngine.php`, 2026-10-26).
48. **`Collection::reject()` with no argument does NOT filter falsy values in Laravel 12.** The signature is `reject($callback = true)`, so the keep-condition is loose `$value != true`; `null` survives (`null != true` is true) and only literal `true` entries are rejected. A `->map(... null ...)->reject()->sort()` chain silently iterated `null` items and crashed with "Trying to access array offset on null". Rule: use `->filter()` to drop falsy/null entries, or pass an explicit callback (`app/Services/KpiReportInsightsService.php`, `gapInsights`, 2026-10-26).
49. **Untracked working-tree files can vanish between tool calls.** `tests/Feature/Mcp/KpiToolsTest.php` (never committed) was deleted by an external process mid-session; the only reliable recovery was the Windows Recycle Bin (`C:\$Recycle.Bin\<SID>\$R*.php`). Rule: commit work-in-progress untracked feature files early, and if a read/edit that previously succeeded suddenly reports "File not found", check the Recycle Bin and `git status` before assuming the work is writable again.
46. **Blade `{!! nl2br(e($task->description)) !!}` escapes HTML tags into visible literal entities when data contains rich text HTML.** Task descriptions in Plamx are rich text HTML (e.g. `<p>...</p>`). Wrapping them in `e()` converts `<p>` into `&lt;p&gt;`, displaying literal `<p>` tags on screen in views such as approval requests. Rule: render rich text with safe tag stripping `{!! strip_tags($task->description, '<p><br><b><strong><i><u><ul><ol><li><a>') !!}` rather than `e()`, and ensure all dynamic and parameterized translation keys (e.g. `:task_term Context`, `Associated :task_term`) exist in `resources/lang/ar.json` so English fallbacks do not leak into the Arabic UI (`resources/views/tenant/approvals/show.blade.php`, `resources/lang/ar.json`, 2026-10-26).
50. **"مؤشرات فرعية مرتبطة" (linked sub-KPIs) means dynamic relations, NOT leading/lagging KPIs.** A Plamx KPI has two unrelated KPI-to-KPI models: (1) `kpi_dynamic_relations` (`KpiDynamicRelation`, morph) — a dynamic/partially-dynamic KPI is *computed from* its related KPIs/projects/tasks, each with `relative_weight`; these are what users mean by مؤشرات فرعية, and `get-kpi-dynamic-relations-tool` answers them. (2) `kpi_performance_relations` (`leadingKpis`/`laggingKpis`, `performance_kpi_type` leading/lagging) — a separate performance model that is NOT sub-KPIs. ChatGPT answered a sub-KPI question with the leading/lagging list, so the MCP descriptions + server instructions now explicitly say to use dynamic relations for that intent (`app/Mcp/Tools/Kpis/GetKpiDynamicRelationsTool.php`, `PlamxServer` instructions, 2026-10-27).
48. **Task serialization with dynamic approval accessors in `$appends` produces severe N+1 query storms unless batched.** When models define accessors like `has_pending_approval`, `due_date_deferred_for_approval`, etc. in `$appends`, every task converted to JSON runs individual `exists()` queries if `pendingApprovalRequests` is not loaded. For 500 tasks, this causes 2,000+ queries. In addition, `WorkTeamMember::with(['tasks'])` was pulling full task models for every team member just to count `.length` in UI. Rule: use request-scoped static maps (`Task::getActiveApprovalsMap()`) to resolve pending approval states across any task in 1 single tenant query, use `WorkTeamMember::withCount('tasks')` instead of loading entire task collections, and ensure endpoints returning both tasks and members (e.g. `/dashboard/stats/tasks-stats`) are called once by frontend instead of duplicated in parallel (`app/Models/Task.php`, `app/Http/Controllers/Tenant/DashboardController.php`, `resources/views/tenant/dashboards/task-management/main_dashboard.blade.php`, 2026-10-26).
51. **Report and dashboard permissions must be excluded from the general Roles permissions matrix and preserved during role save.** Standalone registries (`resources/reports_permissions.php` and `resources/dashboards_permissions.php`) have their own management screens in Account Settings (`ReportPermissionsController` and `DashboardPermissionsController`). `RolesController::setBaseQueries` must exclude both `category = 'Reports'` and `category = 'Dashboards'` so they do not leak into the Roles modal tree, and `RolesController::afterSave` must merge existing role permissions from those categories before syncing to prevent wiping them (`app/Http/Controllers/Tenant/Settings/RolesController.php`, 2026-10-27).
52. **Never hardcode Arabic fallback terms or assumed methodology entities in controllers or views.** Plamx structure levels are fully tenant-configurable via `terms_management_settings` (`Strategic Structure Level 1/2`, `Operational Structure Level 1`, `Task`, `Sub Task`, `Sub Sub Task`). Never hardcode fallback Arabic strings (e.g. `'المحاور'`, `'المجالات'`, `'الأنشطة'`) in PHP or views; resolve terms strictly via `__terms(...)` or dynamic structure levels (`$methodologyLevels`, `$operationalMethodologyLevels`). Calling generic Laravel `__('Sub Task')` can leak raw placeholder tokens like `:sub_task_term`; always use `__terms(...)` for domain terms (`app/Http/Controllers/Tenant/Plans/StrategicMethodologyOverviewController.php`, `resources/views/tenant/plans/methodology_overview.blade.php`, 2026-10-27).
53. **Working Hours Access 24h timeline positioning and toggle reactivity in account settings.** The visual timeline represents the 24-hour day (1440 minutes) running 00:00 to 24:00 with `dir="ltr"`. Form inputs must not be HTML-`disabled` when days are toggled off to avoid dropping keys from `FormData`/POST requests; use pointer-events / opacity styling and recalculate total working days and weekly hours dynamically (`resources/views/tenant/settings/account-settings/working-hours-access/index.blade.php`, 2026-10-28).
